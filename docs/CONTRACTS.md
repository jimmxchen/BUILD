# Contracts

Everything talks through **one layout JSON**. Change it only by editing all three together
and telling the team:

- `backend/walkthru/schema.py` (source of truth, Pydantic)
- `frontend/src/lib/types.ts`
- this file

## Units and coordinates

- All lengths in **feet**, areas in sq ft.
- Origin = footprint's **top-left** corner. `x` grows east, `y` grows south.
- Rooms are axis-aligned rectangles `x, y, w, h`, snapped to a **0.5 ft grid** (the 3D wall
  builder relies on this).
- `footprint.width_ft/depth_ft` are bounding dimensions. For an irregular footprint,
  `footprint.outline` is an optional ordered orthogonal boundary of the union of room rectangles;
  `footprint.holes` lists any enclosed courtyard boundaries. Vertices lie on the 0.5 ft grid.
  When `outline` is absent, rooms must tile the full bounding rectangle as before.
  The actual building area is the room union, excluding any holes.
- 3D: 1 three.js unit = 1 ft. Plan `(x, y)` maps to three `(x, z)`; `y` up. Eye height 5.5 ft,
  wall height 9 ft, wall thickness 0.33 ft.
- `"exterior"` is a pseudo-room id used in `Door.between` for the front door.

## Layout JSON

The planner fills rooms without positions (`RoomProgram`); the solver adds `x, y, w, h`,
doors and windows; the checker adds `checks`.

```json
{
  "footprint": {"width_ft": 50, "depth_ft": 36},
  "entrance": {"x": 25, "y": 36},
  "requested_sqft": 1800,
  "rooms": [
    {"id": "kitchen", "type": "kitchen", "name": "Kitchen",
     "target_sqft": 180, "adjacent_to": ["dining"],
     "x": 0, "y": 0, "w": 15, "h": 12}
  ],
  "doors": [{"between": ["kitchen", "hall"], "x": 15, "y": 4, "width_ft": 2.67}],
  "windows": [{"room": "kitchen", "wall": "south", "offset_ft": 4, "width_ft": 4}],
  "checks": [{"rule": "bedroom_exterior_wall", "pass": true, "message": ""}]
}
```

- `type` ∈ `living kitchen dining bedroom primary_bedroom bathroom office laundry entry hall closet`
- `Door.x, y` = center of the opening, lying **on** the shared wall.
- `Window.offset_ft` measured from the wall's west end (north/south walls) or north end (east/west walls).

Full example: [`shared/sample_layout.json`](../shared/sample_layout.json) (generated by the baseline
solver from the canned program; regenerate with the snippet in the README).

## RoomProgram (planner ↔ solver)

```json
{"requested_sqft": 1800, "aspect_ratio": 1.4, "notes": "…",
 "rooms": [{"id": "bedroom_2", "type": "bedroom", "name": "Bedroom 2", "target_sqft": 130, "adjacent_to": []}]}
```

No positions, no halls (the solver adds circulation).

## Checker messages (role 1 ↔ role 3)

`Check.message` is plain English, names the room, says what is wrong and by how much.
Multiple problems for one rule are joined with `; `. These strings go **verbatim** into the
fix prompt as `"<rule>: <message>"`.

| rule id | meaning |
|---|---|
| `no_overlap_in_footprint` | no two rooms overlap; all inside footprint |
| `contract_integrity` | unique room IDs; finite geometry on the 0.5 ft grid |
| `door_geometry` | doors fit a shared/exterior wall; front door matches entrance |
| `prompt_fidelity` | explicit room requests from the prompt appear in the plan (generation gate) |
| `all_rooms_reachable` | every room reachable from the front door through doors |
| `bedroom_exterior_wall` | every bedroom has an exterior wall and a door |
| `public_bathroom` | ≥1 bathroom reachable without passing through a bedroom |
| `kitchen_adjacent` | kitchen shares ≥3 ft of wall with dining or living |
| `min_hall_and_door_width` | halls ≥ 3 ft, doors ≥ 2'8" (2.67 ft) |
| `sizes_within_10pct` | each room within 10% of target; house within 10% of requested |

## API (role 6 ↔ everyone)

Base URL `NEXT_PUBLIC_API_URL` (default `http://localhost:8000`).

| method | path | body | returns |
|---|---|---|---|
| GET | `/health` | | `{ok, model, offline}` |
| GET | `/api/sample` | | `GenerateResponse` (no Claude call) |
| POST | `/api/generate[?cached=true]` | `{prompt}` | `GenerateResponse` |
| POST | `/api/edit` | `{program, layout, instruction}` | `GenerateResponse` |
| POST | `/api/chat` | `ChatRequest` | `ChatResponse` (see below) |

```ts
GenerateResponse = {
  layout: Layout, program: RoomProgram,
  rounds: [{round, failed: Check[], note}],   // one per failed check pass
  attempts: number, elapsed_s: number,
  cached: boolean                              // true = backup generation; say so in the demo
}
```

On generation failure the API serves a validated file from `backend/cached/`
with `cached: true` (disable with `WALKTHRU_CACHE_FALLBACK=0`). It prefers a
backup matching explicit bedroom, bathroom, office, and square-footage requests;
if none match, it chooses any valid backup. `?cached=true` uses the same selection.

### Chat (`POST /api/chat`)

One turn of the design conversation. The client sends the whole conversation each time,
plus the current plan (both `null` before a house exists); the server decides what to do.

```ts
ChatRequest  = { messages: {role: "user" | "assistant", content: string}[],  // last = newest user message
                 program: RoomProgram | null, layout: Layout | null }
ChatResponse = { action: "ask" | "answer" | "edit" | "generate",
                 reply: string,             // shown in the chat
                 options: string[],         // 0-4 tappable answers ("3 bedrooms", room names) or next-step ideas
                 brief: string | null,      // generate: refined brief -> POST /api/generate {prompt: brief}
                 result: GenerateResponse | null }  // edit: the edited plan (already run through pipeline.edit)
```

- **ask**: brief too vague (no size and no bedroom count) or the change is ambiguous
  ("make it bigger": which room?). At most 2 questions in a row before a house exists; then it
  generates with defaults and says what it assumed. Tapping an option sends it as the next user message.
- **generate**: no house yet and the brief is clear enough, or the user wants a different house
  ("start over", "new house"). The client calls `/api/generate` with `brief`.
- **edit**: a concrete change. The server derives a one-sentence instruction and runs
  `pipeline.edit`; `reply` gives exact before/after sizes and check status. If the edit fails
  the response is `answer` explaining why (never a 500).
- **answer**: questions about the plan (room sizes, total sq ft), answered from the layout.

With an API key, Claude decides in one structured-output call (`prompts.CHAT_SYSTEM`). With
`WALKTHRU_OFFLINE=1` keyword heuristics stand in; offline edits come back unchanged (the offline
planner doesn't edit) and the reply says so.
